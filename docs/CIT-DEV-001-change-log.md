# CIT-DEV-001 — سجل التنفيذ

## تغييرات محلية على فرع `development`

- وحّدت مفاتيح الهوية والعلاقات المستهدفة في Drizzle على `INT`، وأضافت المخططات فهرسًا مركبًا فريدًا لـ`persons(id, userId)` وقيدي FK مركبين يفرضان أن `business_entities.ownerPersonId` و`business_memberships.personId` يعودان إلى الشخص المرتبط بالمستخدم نفسه. هذا يمنع ربط مالك أو عضو بسجل شخص يخص حسابًا آخر.
- جعلت إنشاء النشاط التجاري ومعه سجل العضوية `owner/active` وسجل التدقيق معاملة ذرية واحدة. تُقفل هوية الشخص أثناء فحص الاستثناء لتجنب استهلاكه بالتزامن.
- يمر استثناء KYC الأولي فقط إذا تطابق OAuth `openId` تمامًا مع `OWNER_OPEN_ID` وكان دور المستخدم `owner`. يُستهلك مرة واحدة على سجل الشخص، ويُسجل حدث تدقيق مستقل، ولا يغيّر حالة KYC إلى `verified`. بقية المستخدمين ما زالوا يحتاجون KYC ساريًا.
- أضيفت اختبارات وحدة لاستثناء المؤسس وأنواع المفاتيح، واختبار تكامل يغطي إنشاء المستخدم والنشاط والمالك والعضوية النشطة، منع ربط person بحساب آخر، منع تحديث المشاهد، القراءة والتحديث المصرح بهما، ومنع تكرار الاستثناء.
- عولج تعارض الترحيلات الذي ظهر أثناء اختبار قاعدة فارغة: قصّرت أسماء القيود الثلاثة في `0009` لتتوافق مع أسماء المخطط، ووحّدت اسم قيد الإضافة الذاتية في `0005` مع ما يتوقعه `0014`. كان `0013` يحاول حذف أسماء لا تنشئها ملفات الترحيل السابقة؛ أصبح خطوة no-op للسلاسل الجديدة، وأضيف أمر اختياري `db:normalize-fks` لتطبيع أسماء قديمة فقط بعد تحديد الهدف صراحةً بأنه `development`. الأمر افتراضيًا dry-run ولا يكتب إلا مع `--apply`.
- أضيف ملف SQL read-only لفحص أنواع أعمدة الهوية وعدم تطابق روابط owner/person/عضوية قبل تطبيق ترحيل التطوير. لا يحذف أو يصلح السجلات تلقائيًا.

## التحقق المحلي

- يسجل التحقق المحلي السابق نجاح `pnpm drizzle-kit migrate` على قاعدة MariaDB اصطناعية فارغة، مع 18 migration حتى `0017`، واختبار تكامل الملكية، واختباري وحدة، و`pnpm check` و`pnpm build` و`git diff --check`.
- هذه النتائج سُجلت قبل عزل CIT وتحديث `development` إلى أحدث `main`؛ لم تُعد الاختبارات أو الترحيلات على النسخة المعزولة التزامًا بتعليمات CIT-DEV-002. على أساس `main` الحالي، migration CIT المستقل مولّد كـ`0016_cit_dev_001_owner_integrity.sql` ولم يُطبق على أي قاعدة.
- أظهر البناء السابق تحذيرات إعدادات Analytics غير المعينة (`VITE_ANALYTICS_ENDPOINT` و`VITE_ANALYTICS_WEBSITE_ID`) لكنه اكتمل بنجاح.
- نجاح MariaDB محليًا ليس بديلًا عن اختبار TiDB الخاص ببيئة Preview. توثيق TiDB يشترط تطابق أنواع أعمدة FK والعمود المرجعي، ويوثق دعم إضافة/حذف FK عبر `ALTER TABLE`.[1] [2]

## ما لم يُنفذ بعد

- لم أغيّر إعدادات Vercel أو TiDB، ولم أضع `DATABASE_URL` لبيئة Preview، ولم أُنشئ deployment أو رابط Preview.
- لم ألمس `main` أو إعدادات Production أو قاعدة الإنتاج، ولم أطبّق ترحيلًا خارجيًا أو أحذف بيانات.
- حُفظت التغييرات المحلية المختلطة (بما فيها Didit وواجهة تسجيل الدخول) في نسخة احتياطية محلية و`stash@{0}`؛ لم تُضمّن في التغييرات المعزولة الخاصة بـCIT.
- لا تزال مطابقة أنواع الأعمدة الفعلية في قاعدة TiDB التطويرية، نتيجة SQL preflight عليها، وربط Preview بقاعدة التطوير، وإنشاء مستخدم اختباري فيها، خطوات غير منجزة حتى يتاح اعتماد Vercel والوصول الآمن إلى قاعدة التطوير.

## الملفات المساعدة

- `scripts/preflight-business-owner-links.sql`: فحص read-only لقاعدة التطوير قبل الترحيل.
- `scripts/normalizeLegacyForeignKeys.ts`: dry-run افتراضي لتطبيع أسماء FK القديمة؛ يحتاج `DATABASE_TARGET=development` و`--apply` للكتابة.
